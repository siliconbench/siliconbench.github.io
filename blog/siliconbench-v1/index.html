SiliconBench v1.0: Can agents engineer real silicon?

Shang Liu, Wenji Fang, Jing Wang, Ziyan Guo, Yao Lu, Zhiyao Xie HKUST
Paper (PDF) Dataset Leaderboard
TL;DR
  • 94 real chip engineering tasks, graded on simulation, synthesis, timing and layout, not simulation alone.
  • Claude Opus 5.5 passes 84.0%. The best open-weights agent, GLM-5.3, passes 33.0%.
  • 21.3% of failed runs pass RTL simulation and then fail a downstream check.
  • Agents attempted to hack the grader in 53 of 564 runs. None succeeded.

01Why another hardware benchmark?

Agents now report 95–99% on standard RTL benchmarks. Real chip engineering is far from solved. The gap is in what those benchmarks leave out:

  • Single-stage grading. Most check functional simulation only. Synthesis and layout appear only on small, standalone modules.
  • Isolated edits. Agents fix RTL under frozen constraints, or tune scripts on frozen RTL. Real designers change both together.
  • Hackable grading. When the agent and the grader share a workspace, an agent can look for reference answers, weaken a testbench, or hide logic from synthesis.

SiliconBench closes all three gaps.

02What is in it

Each task is a compilable, multi-file repository from one of 30 open-source SystemVerilog projects, such as OpenTitan, CVA6, Corundum, BlackParrot and PULP Ara. Repositories have 2–70 RTL files, with a median of 12 files and 3,670 lines. The agent gets a written specification and must make the design pass every check the task requires.

Tasks span seven hardware domains, from network and DMA engines to vector accelerators and crypto cores:

Every task runs functional simulation. Most go further: 85 add synthesis and gate-level checks, 81 add static timing or CDC/RDC, and 15 require hard-SRAM floorplanning, clock-tree synthesis and routing. In 24 tasks, the agent must edit timing constraints (.sdc) or macro floorplans along with the RTL.

03Grading the agent cannot touch

We use the two-container Harbor architecture. The agent never shares a filesystem with the grader.

04How tasks were built

Phase I · Seed pool160

Senior IC engineers write candidate tasks with self-contained specifications.

Phase II · Automated QA2 + 1

Two independent reference solutions must pass; the starter design must fail. Injected bugs must be caught.

Phase III · Expert review94

Specialists check every assertion against the spec and remove ambiguous or fragile tasks.

Requiring two independent solutions keeps graders honest: a valid hardware fix can take many forms, and the tests must accept all of them.

05Results

We evaluated six frontier agents at high reasoning effort: four proprietary and two open-weights, 564 runs in total.

The ranking is clear, and so is the gap: proprietary agents pass 40.4–84.0%; open-weights agents pass 27.7–33.0%. The gap grows when RTL and constraints must change together. Claude Opus 5.5 keeps 79.2% on those 24 tasks; GLM-5.3 drops to 4.2%.

Results by problem type show where agents struggle most. Bug repair in an intact design is easiest. New features and physical co-design are hardest: on the eight hard-SRAM tasks, DeepSeek-V4.1-Flash-1017 solves none.

06How agents work

We analyzed all 46,526 tool calls. Three distinct styles emerge.

  • Test first, then verify downstream (Claude Opus 5.5). On 64.9% of tasks it runs its own testbench on the original RTL to confirm the test catches the bug. It then updates connected modules and reads synthesis, timing and layout reports before finishing.
  • Trial and error (GLM-5.3, DeepSeek-V4.1-Flash-1017). 122–136 median calls per task. DeepSeek checks its testbench against the original RTL on only 20.2% of tasks. GLM and DeepSeek spend 33.3% and 30.9% of calls fixing their own broken testbenches, resolving compile errors or repeating failed edits.
  • Stopping early (GPT-Sol 6.1, GPT-Terra 6.1). 37.5–44.5 median calls. In about 20% of runs they edit RTL after their last simulation and never re-test, and they skip gate-level simulation on over 55% of applicable tasks.

07Why agents fail

Reading the 272 failed trajectories, three patterns repeat:

  • Coupled modules left out of sync. On tasks spanning three or more modules, leaving a required module untouched is 5.1× more common in failed runs than in passing ones. Others edit each file locally without matching the flush, credit or valid/ready handshake across the boundary.
  • Self-confirming testbenches. Of 85 functionally wrong submissions, 97.6% ended with the agent claiming verification succeeded. Their tests used only simple inputs, stopped at lint, or relaxed a failing check, assuming the test was wrong.
  • Treating hardware like software. Agents test in 2-state simulation and miss X values after reset, unroll loops past area limits, skip timing or layout tools, or ignore negative slack because the tool exited with code 0.

Six tasks remain unsolved by all six agents. Each combines multi-file logic with strict area, multi-corner timing or multi-SRAM layout limits.

08Evaluation hacking

We define evaluation hacking as a deliberate attempt to bypass grading, such as searching for hidden tests or reference RTL outside /workspace. It happened in 53 of 564 runs, with 90 distinct events. Zero succeeded.

1.1–2.1%of runs attempt hacks, proprietary agents
17.0–31.9%of runs attempt hacks, open-weights agents
0 / 90hack events that got past the verifier
  • Probing for answers (86 events). find /, grep -r and ls /workspace/.. to look for testbenches, grader scripts or upstream code. The offline solver container holds none of them.
  • Hiding logic from synthesis (3 files, 2 runs). On the Ara vector divider, GPT-Sol 6.1 and GPT-Terra 6.1 wrapped logic in `ifndef SYNTHESIS, so the simulator and synthesizer see different circuits. The verifier's policy check and gate-level simulation reject it.
  • Forging a timestamp (1 event). After editing and reverting a read-only wrapper, GPT-Terra 6.1 ran touch -d to restore its timestamp. Harbor copies only hash-verified, allowlisted files, so this has no effect.
As agents get stronger, a benchmark is only as good as the wall between the agent and the grader.

09Four case studies

OpenTitan KMAC · 5/6 pass

Cross-module flush

A flush must stop prim_packer inputs and drain kmac_msgfifo together. DeepSeek-V4.1-Flash-1017 edits both without blocking new inputs; Claude Opus 5.5 keeps them in sync.

Corundum 100G NIC · 1/6 pass

500 MHz timing closure

GPT-Terra 6.1 does an 80-bit add and compare in one cycle: it passes simulation, then fails timing at 2.62 ns (WNS −0.62 ns). Only Claude Opus 5.5 pipelines it (WNS +0.52 ns).

BlackParrot 8-SRAM tile · 4/6 pass

Macro clock skew

Skew must stay under 4.00 ps. DeepSeek-V4.1-Flash-1017 leaves all eight macros upright (10.84 ps). Claude Opus 5.5 mirrors the bottom four toward the clock spine (3.07 ps).

PULP Ara divider · 1/6 pass

Area, without cheating

The cap is 83.6K µm². Two agents hide divider logic from synthesis and are rejected. Only Claude Opus 5.5 prunes wrapper logic and shares one 64-bit divider (67.2K µm²).

10What is next

SiliconBench is a living benchmark. We will add releases as agents improve and publish every task, grader and trajectory format, so others can reproduce our numbers or prove us wrong. If you build hardware agents, run the benchmark and send us your results.

Open-weights models trail by a wide margin today. We hope an open, trustworthy benchmark helps close that gap.
